# Scratch KEIKO — Scratch API継続検証

Scratchの検索・一覧から得られる作品IDと累計統計を測り、同一作品の個別APIと比較する実験。Python 3.11以上、標準ライブラリのみ。実際の初回測定は [reports/pilot/REPORT.md](reports/pilot/REPORT.md)、元記録は [data/pilot](data/pilot) に同梱。

## すぐ結果を見る

フォルダを展開して、このREADMEがある場所で実行する。

```sh
python3 report.py --data data/pilot --out reports/rebuilt-pilot
python3 -m unittest -v
```

レポートの再生成と合成データによるテストはオフラインで動く。追加の実測をローカルで行う場合は、別の保存先を指定する。

```sh
python3 keiko_probe.py --data data/local-pilot
python3 report.py --data data/local-pilot --out reports/local-pilot
```

以前のZIPから、取得先の設計、欠損をゼロにしない統計処理、2026年11月5日の記録と再計算用スクリプトを引き継いだ。11月5日の観測は [historical](historical) にあり、取得経路が異なるので今回のHTTP成功率や処理時間の分母には入れない。台帳にあった作品、利用者、スタジオと照合方法を初期設定に反映した。

## GitHub Actionsで28日間の測定を始める

1. 自分のGitHubに専用リポジトリを作る。公開設定なら、同梱の観測データや今後の観測結果も公開される。公開リポジトリの標準GitHub-hosted runnerは無料。非公開リポジトリの時間・保存枠は契約による。
2. ZIP内のこのフォルダの中身をリポジトリのルートへ置く。`.github/workflows/keiko-observe.yml` も含め、デフォルトブランチへコミットしてプッシュする。GitHubの画面でZIPをそのままアップロードするとワークフローとして認識されない。
3. **Actions → KEIKO 28-day API observation → Run workflow** を開き、デフォルトブランチを選ぶ。**start_campaign** をオンにして実行する。GitHub内蔵の `GITHUB_TOKEN` で結果をコミットするため、リポジトリまたは組織の設定でワークフローへの `contents: write` を許可する。別途APIキーは不要。
4. 初回実行で **Preserve observations and final report** が成功し、`data/campaign/campaign.json` と `data/campaign/runs/*.jsonl` がコミットされたことを確認する。各実行の **Summary** と **Artifacts → keiko-…** で集計を確認できる。初回の同梱済みパイロットとキャンペーンの結果は別ディレクトリに保存する。

専用リポジトリでは、初回起動だけを指示する `.github/keiko-start` のコミットでも開始できる。開始済みのキャンペーンでは、このファイルを変更しても開始日時を更新しない。

コミット済みデータを取り出して、任意の時点で再集計できる。

```sh
git pull
python3 report.py --data data/campaign --out reports/campaign
```

起動候補は毎日 **01:17、03:17、05:17、…、23:17 JST**（2時間ごと）。キャンペーン開始から28日間を6時間枠に分ける。今回の開始時刻に対して、各枠の開始から約28分・2時間28分・4時間28分後に起動候補がある。すでに終了記録がある枠ではScratch APIの取得を省略する。起動時刻はGitHubの遅延・欠落に左右されるため、全112枠の観測を保証するものではない。28日経過後はScratch APIの取得を停止し、次に実行されたジョブで最終レポートをGitへ保存する。欠測枠は実際のログを基に集計する。途中停止・再開はActions画面から行い、停止中の期間も観測期間に含まれる。

参考 [GitHub Actionsの定期実行](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule)、[トークン権限](https://docs.github.com/en/actions/security-for-github-actions/security-guides/automatic-token-authentication)、[料金と使用量](https://docs.github.com/en/actions/concepts/billing-and-usage)。

## 28日後の結果とAirtable

- 観測記録はデフォルトブランチの `data/campaign/runs/` に順次コミットされる。
- 28日の期限後に最初に動いたジョブが `reports/final/REPORT.md`、`summary.json`、各CSV、欠測枠を含む `completion.json` を生成し、デフォルトブランチにコミットする。GitHubの実行遅延によって、最終集計時刻は観測期限より後になる。
- レポートのpush成功後、Airtableの既存「検証計画」テーブルにキャンペーン開始時刻をキーに最終集計を追加・更新する。再試行で同じ観測の記録を重複作成しない。成功時は `reports/final/airtable_receipt.json` にレコードURLが残る。
- Airtableのトークンが未設定でもGitHubへの最終レポート保存は行われる。最終化後のジョブは、Airtable未登録の場合だけ登録を試行する。登録まで済むと以後のジョブは状態確認だけで終わる。

Airtableの自動記録を有効にするには、台帳を書き込めるアカウントで [Airtable Personal Access Token](https://airtable.com/create/tokens) を発行する。Scope は `data.records:write`、アクセス先は「Scratch KEIKO｜技術調査・設計台帳」。GitHubの **Settings → Secrets and variables → Actions → New repository secret** に `AIRTABLE_PAT` として保存する。トークンをコードやチャットに貼る必要はない。期限後に追加した場合は、次の定期実行または `start_campaign` オフの手動実行で登録できる。

## 測定条件

- 毎日の最初の観測枠で検索、Explore、作者、お気に入り、スタジオ、トップページを取得する。公開活動・ハート一覧は初日に全設定対象、その後は交互に取得する。検索の言語指定は日本語・英語・スペイン語。題材、言語設定、共有履歴の違う経路を選んだ便宜標本で、国別閲覧の推定には使わない。
- 作品 `1399147684` を全観測枠で取得し、旧・新題名の検索を日次に行う。タイトル検索は指定文字列による通常検索で、検索APIに完全一致機能があるという前提は置かない。
- 固定比較標本は、最初に有効な一覧を取得できた日に作者一覧、コミュニティ経路、検索系から最大2件ずつ抽出する。検索系以外を先に抽出し、固定シードによるIDのハッシュ順と、グループ内で取得先1つにつき最大1件という条件を使う。標本は `panel.json` に固定する。日次で、検索以外から選んだ最大4件の題名を別に検索する。
- 通常は個別APIを1枠最大7作品、日次の追加取得込みで約40〜46経路。デフォルトでリクエスト開始間隔2秒以上、最大2並列、試行上限64回、タイムアウト18秒、再試行1回。上限は再試行込み。明示的なキャッシュバイパス、プロキシの追加、ログイン、Firecrawlは使わない。
- `config.json` で間隔、上限、並列数、対象、急増の仮閾値などを変えられる。比較条件を固定するため、開始済みキャンペーンでは設定の変更を検出して停止する。設定を変えて試すときは、別ディレクトリまたは専用の別リポジトリで行う。
- 数時間単位の遅れは記録する。評価の焦点は、別のHTTP応答が返った後にも数日・数週間残る不一致。観測間隔より短い更新時刻や、元DBと多段キャッシュの内部状態は観測できない。

## 記録と指標

| 出力 | 内容 |
| --- | --- |
| `data/*/runs/*.jsonl` | 1実行1ファイル。HTTP試行ごとにUTC時刻、経路、ステータス、所要時間、読み取った本文サイズ、選定したヘッダー、本文SHA-256、正規化した作品データを保存。検索の0件は有効な空応答として扱う |
| `observations.csv` | 取得元、作品ID、タイトル、作成・共有・最終更新日時、3指標、キャッシュヘッダーなど |
| `list_detail.csv` | 同一実行・同一IDの時刻差、3指標差、タイトル・最終更新等の一致 |
| `title_checks.csv` | 旧・新題名と独立標本の題名検索、各照合の対象ID有無。失敗時は不明 |
| `overlap.csv` | 経路の組ごとの共通ID数とJaccard係数 |
| `update_cadence.csv` | 比較できた観測の間隔、一覧値・個別値の変化回数、個別値だけが変化した回数 |
| `discrepancy_spans.csv` | 比較で不一致が観測された期間幅、観測間隔、HTTPヘッダーの変化。単発の幅は0時間で、原因や継続期間を確定しない |
| `summary.json` / `REPORT.md` | API別成功率、独自ID、重複、通信量、応答時間、固定事例、独立標本、4方式の比較、失敗 |

作品情報の生レスポンス、認証情報、コメント、作品コードは保存しない。累計値が欠けた行は空欄。ハート・活動HTMLでは作品へのリンクを抽出する。ハート一覧の画像・題名リンクは同じIDを指す場合があるため、行とIDを別に計数する。HTMLの構造を認識できない場合は200でも解析失敗とする。本文バイトはコードが実際に読み取った分で、圧縮が返れば圧縮サイズ。HTTPヘッダーやエラー本文のサイズは含まない。

API別の独自IDは測定した他の発見経路に現れなかったID。タイトル照合専用の検索を発見数から除く。共有時期はAPIが日時を提供した行から集計する。個別作品APIと比較できるのは固定標本のうち両方の応答に出た作品で、全件の鮮度評価ではない。低Ageでも差が残る場合は一覧側の供給データが古い可能性を示すが、単独では内部原因を確定しない。

## 4方式の比較方法

個別参照の実測履歴から、個別全件、一覧日次、一覧日次＋不足分の個別、さらに前回までの変化に応じた追加個別を同じ固定標本で再生する。4方式を別々にオンライン実行した記録ではない。通信量と応答時間の合計は、再生時に選んだ実測リクエストから求める。各方式の実時間や大規模運用の処理時間は別途測定が必要。Ageが得られる一覧は12時間超を一括側の採用から外し、Age不明は採用した上で元データ鮮度は不明とする。

観測頻度の削減と一括取得自体の効果を分けるため、同じ日に30分以内に観測できた作品だけの比較も出す。取得済みページを事後に選ぶため、実運用で最適な一覧を事前に選べるという保証にはならない。

急増は4～8時間の観測差を6時間換算し、閲覧100、ハート10、お気に入り5のいずれか以上を暫定判定に使う。個別参照で急増した枠を分母とし、方式に比較可能な短い観測窓がない場合と、比較できたが閾値に届かない場合を別集計する。単発の初回測定では `0/0` となる。

初回は45試行・約142秒・正規化ログ約267KB。単純に日次28回と残り84回に展開すると、固定標本が毎回7件の場合で約1,700試行、観測ログは10MB前後が目安。これはパイロットからの推計で、429、再試行、応答の大きさ、実際の枠数によって変わる。設定上の上限は112枠×64試行＝7,168試行。中断後の同枠再実行で新しいログが追加される場合は、この積は累計の厳密な上限ではない。

## 障害からの復旧

| 状況 | 確認・対処 |
| --- | --- |
| 429・5xx・タイムアウト | バックオフして設定回数内で再試行する。長い `Retry-After` はログに再開可能時刻を残し、その実行は停止。429が続く場合は追加取得を止める |
| 200だが解析失敗 | ログの `error` と `Content-Type` を見る。正常な空配列や既知構造の空活動欄とは区別される |
| 途中で処理が停止 | JSONLに完了済みの試行を逐次記録。GNU timeoutで観測処理を10分に制限し、残り時間で保存ステップを実行する。途中で切れた最終行は再集計時に無視する |
| コミットやpushが拒否された | Actionsのログで書き込み権限やブランチ保護を確認する。Artifactsの復旧コピーをダウンロードし、`data/campaign/` にまだないファイルだけ追加してコミットする。同名ファイルの内容が異なる場合は手動で照合する |
| ランナーが強制終了、または保存とArtifactの両方に失敗 | 既にコミット済みの測定はリポジトリに残る。今回のランナー内のデータは回収できない場合があり、欠測として扱う |
| 定期実行の結果がない | デフォルトブランチ、Actions有効状態、`campaign.json`、実行時刻、同枠完了・期限・冷却期間のメッセージを確認する。すでに開始済みなら `start_campaign` をオフのまま手動実行できる |

GitHub Pagesの設定は不要。Actionsの集計とコミット済みデータで確認できる。
